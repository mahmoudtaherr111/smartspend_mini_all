## 1. الحالة الفعلية قبل البدء

هذه المساحة هي النسخة الموحدة المنشورة على `main`. افحص `git status` ووسم الإصدار وmanifest التسليم قبل أي تعديل، ولا تطبق patch تاريخية فوقها عمياء.

Codex نفّذ الجزء المعقد من هذه الجولة: تحديد الحدث المالي قبل الفئة، ربط المبالغ بالمقاطع، استبعاد النفي والمستقبل في الحالات المدعومة، إبقاء العمليات ناقصة المبلغ معلقة، معالجة التصحيح المباشر والإجماليات، ومنع دمج الفئة والمعايرة والتحقق من اختراع حقائق مالية. استخدم أيضًا إصلاحات Claude A1 وراجعها واختبرها مع النواة.

تسليم Claude A2 التاريخي محفوظ في `docs/reviews/implementation/A2/`. دُمجت الأجزاء المراجعة منه في هذه النسخة، مع استثناء floor مدة الصوت غير السليم. لا تستخدم أرقام HANDOFF التاريخية بدل الاختبارات والقياسات في `main`.

## 3. هدف المنتج والأولويات

المستخدم مصري يسجل باللهجة المصرية وبأي ترتيب، وقد يذكر دخلًا أو تحويلًا أو دينًا أو استردادًا، أو عدة عمليات أو معلومة ناقصة.

Voice → STT → normalization → financial events/entities → amount binding → category → evidence/calibration → selective LLM → validation → review/clarification → persistence → display/correction/learning.

الأولوية للدقة، ثم السرعة، ثم التكلفة دون إضعاف غير مقبول للدقة. استخدم المحلي حين تكفي الأدلة؛ LLM حين يمكنه حل غموض موجود بالنص؛ وسؤال المستخدم حين تنقص المعلومة أصلًا. لا تعد بدقة 100%، ولا ترفع الثقة لتجميل النتيجة، ولا تجعل كل شيء review أو LLM للتحايل على القياس.

## 5. G1 — المطلوب منك فعليًا

هذه أعمال دعم محدودة، تترك القرارات الدلالية والمالية الحساسة لجولة مراجعة مستقلة.

### G1.1 أمر تحقق موحد وربطه بـCI

- افحص package.json وCI الحالية. npm run test في هذه النسخة يشغل قائمة معينة؛ لا تفترض أنه يغطي التصنيف كله.
- أضف أمرًا مثل test:classification:core يشغل ملفات القبول والنواة والجودة الحالية، دون تغيير thresholds أو expected results.
- اربطه بمسار CI القائم إن وجد؛ وإلا أضف job محدودًا وفق بنية المشروع، ببيانات اصطناعية ودون مزود مدفوع.
- حافظ على الاختبارات الأخرى وruntime المعتمد، ولا تكرر workflows أو تضف dependencies دون حاجة مثبتة.
- أثبت أن فشل quality gate يجعل الأمر/job يفشل. يمكن mutation مؤقتة في مساحة اختبار ثم إعادتها؛ لا تسلّم اختبارًا مخففًا.

### G1.2 تقرير نتائج آلي قابل للمقارنة

- ولّد التقرير من scoring الحالية دون تعديل المصنف أو محاذاة النتائج كي تتحسن الأرقام.
- سجّل hash للـfixtures، نسخة الكود/ملفات النطاق، إعدادات التشغيل، offline/scripted/live، وزمن التشغيل.
- اعرض baseline/candidate وdelta لـrecord F1، amount F1، precision/recall لكل فئة، confusion matrix، type accuracy، وعدد auto_save/review/clarify والأخطاء داخل كل قرار.
- افصل unsafeAutoSaves / كل الحالات عن الأخطاء / حالات auto_save. اكتب المقام وتعريف المطابقة وكيف عالجت allowedCategories والنتائج غير المطابقة.
- قارن نفس البيانات والإعدادات فقط. استخدم matches من scorer القائم بدل المحاذاة حسب index، وبيّن حدودها عند تساوي المبالغ.
- llmCalls الحالي مشتق من parsedBy ولا يمثل طلبات الشبكة أو retries. سمّه derivedLlmRoutes أو ضع توضيحًا صريحًا دون كسر العقود القائمة.
- صفر tokens في offline لا يعني تكلفة إنتاج صفرًا. لا تستنتج تحسن STT أو p95 إنتاجيًا من اختبار بلا شبكة.
- التقرير الافتراضي ملخص خالٍ من النصوص المالية وأسماء الأشخاص والمفاتيح؛ التفاصيل الاصطناعية اختيارية. لا تطبع ملف الأدلة كله.

### G1.3 تحديث الوثائق التشغيلية

- حدّث docs/03-AI_CLASSIFICATION_ENGINE.md بما تؤكده الاستدعاءات: planFinancialEvents ثم classifyAdmittedEvents ثم بوابات النتيجة، مع موضع الذاكرة والقواعد والـLLM والتحقق الفعلي.
- sourceEventId معرف داخل الطلب، وليس idempotency key أو معرف DB.
- وثّق أن parser_fast_decomposition_enabled القديم لا يعطل بوابة سلامة الأحداث؛ السجل يميز قيمته القديمة من السلوك الفعلي. لا تغيّر semantics الإعداد في G1.
- صحّح التعليقات القريبة المخالفة للتنفيذ فقط. لا تحذف فروعًا قديمة أو تعمل refactor للمصنف.
- وثّق تشغيل الاختبارات والتقرير وحدود النتائج، وحدّث progress بنطاق G1 فقط.

## 6. خارج G1 — لا تنفذه ضمنيًا

- إعادة تصميم الأحداث أو قواعد النفي/الأرقام أو intent/taxonomy أو المعايرة أو fallback.
- إعادة دمج A2 أو إعادة كتابة provider chain/circuit breaker/cache versioning/voice quotas الموجودة.
- اختيار أو hardcoding نموذج جديد. DeepSeek V4 Flash يحتاج تحقق إتاحة فعليًا عبر registry/capabilities ومراجعة المزود؛ الاسم في الكود ليس إثباتًا.
- حفظ العملة والتاريخ، idempotency وclarification replay وملكية المحافظ والأعمال وbatch rollback وoffline identity.
- تعلم تصحيحات المستخدم وأهلية الذاكرة والخصوصية والحذف وحماية Redis الموزعة.
- تحسين benchmark بتغيير البيانات أو توقعاتها أو استثناء الأمثلة الفاشلة.

لو ظهر bug مهم خارج النطاق، أعد إنتاجه بمثال اصطناعي وسجله بدليله؛ لا تعتبره تفويضًا لجولة جديدة. هذه البنود لم تصبح سهلة أو منتهية، بل مؤجلة لمراجعة مستقلة.

## 7. الثوابت الواجب الحفاظ عليها

- الهوية = userId + userType، والمرجع داخل procedures هو ctx.user. لا تستبدل role بـplan.
- Zod للتحقق runtime والعقود المشتركة حين تعبر FE/BE. لا any/ts-ignore أو توسيع نوع لإخفاء عيب.
- ExpenseInputLimits مرجع حدود الإدخال؛ لا توحد الحدود القديمة باجتهاد داخل G1.
- نماذج المنتج عبر model-mapper وai-provider-registry والإعدادات. نموذج كتابة الكود ليس نموذج المنتج بالضرورة.
- الإعدادات عبر getSystemSettings، وبعد كتابة أدمن invalidateSettingsCache.
- UI عربي وRTL وأخطاء TRPC مستقرة دون secrets أو stack traces.
- لا مصنف موازٍ ولا قاموس ثانٍ للوظيفة نفسها. لا تعتمد على اسم الملف لإثبات المسار.
- لا تُرسل بيانات مالية أو صوتية حقيقية إلى مزود خارجي لأجل هذه المرحلة.

## 8. حماية مساحة العمل والتنفيذ

افحص git status وdiff وmanifest واحفظ baseline لملفات G1 قبل تعديلها. لا reset --hard أو clean أو checkout لاسترجاع ملفات المستخدم، ولا تكتب فوق تعديلات موجودة.

إذا أنشأ وضع العمل worktree، انقل الحالة الحالية بما فيها الملفات غير الملتزمة وتحقق من hashes؛ BASE_COMMIT وحده يفقد الجزء الأخير من النواة. اجعل لكل ملف كاتبًا واحدًا. نفذ محليًا الخطوات الضرورية المصرح بها دون طلب موافقة متكرر.

لا commit أو push أو merge أو deploy، ولا db:push/migrate/seed على قاعدة المستخدم، ولا تغيير .env أو تشغيل خدمات خلفية. التسليم محلي وقابل للمراجعة.

افهم → قِس baseline → نفّذ تغييرًا محدودًا → اختبر → قارن → سلّم. Mock حدود الشبكة وقاعدة البيانات فقط، لا الوظيفة التي تزعم اختبارها. سجّل فشل baseline بالاسم ولا تصفه «قديمًا» دون مقارنة فعلية.

## 9. شروط القبول

1. أمر G1 ينجح محليًا ويعيد exit غير صفري عند فشل الجودة، دون شبكة مدفوعة.
2. نجاح npm run check واختبارات G1 والنواة؛ لا regression في الـ551 حالة أو بوابات الجودة الحالية.
3. تقرير صغير معروف الإجابة يثبت precision/recall والمقامات وdelta والتعامل مع فئة غير متوقعة ومبلغ مفقود.
4. التقرير يحمل provenance وينبه بوضوح عند اختلاف fixture hashes.
5. لا تعديل runtime للمصنف أو thresholds أو prompts أو routing أو DB/UI؛ أثبت ذلك بالـdiff.
6. lint بلا مخالفات جديدة؛ افصل المخالفات الموجودة مسبقًا.
7. docs تطابق الكود ولا تدعي اكتمال المنظومة أو دقة 100%.
