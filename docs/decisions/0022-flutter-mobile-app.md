# 0022. A Flutter app in `mobile/`, on the same API, with native code only where the platform demands it

- Status: accepted; milestones 1 (foundation) and 2 (sign-in) are built, in `mobile/` and
  `.github/workflows/mobile.yml`; milestones 3 to 6 are not.
- Decided and recorded: 2026-10-18.

## Context
SmartSpend ships one React build three ways: in the browser, installed as a PWA, and inside Capacitor shells
(`android/`, `ios/`, app id `com.smartspend.app` in `capacitor.config.ts`). Bank and wallet messages reach the API
from a second Android app, the Kotlin companion in `android-app/` (`com.smartspend.sync`), downloaded as a debug
APK from the website, and from an iPhone Shortcut that posts to `/api/sms/ingest?token=…`
([bank messages](../systems/bank-messages.md)).

That leaves three problems a web view cannot solve:
- Two Android apps for one product, the second sideloaded. Since Android 13 a sideloaded app cannot be granted
  notification access without the user first finding "Allow restricted settings" in its App info, and Android 15
  widened that block. An app installed from the Play Store is not restricted.
- The iPhone path depends on a public Shortcut that carries the user's ingest token in its URL.
- The interface is a web page inside a native frame: gestures, sheets, haptics and the keyboard are imitated in
  the browser instead of coming from the platform.

What the code already gives a native client:
- The API runs on its own: `api/server.ts` and `npm run backend:build` deploy it without the web app.
- tRPC is mounted at `/api/trpc/*` with no transformer, so requests and answers are plain JSON
  (`src/providers/trpc.ts`, `api/middleware.ts`); errors carry `data.code`, `data.httpStatus` and an Egyptian
  Arabic `message`.
- `createContext` reads `Authorization: Bearer` before any cookie, and phone accounts already receive their session
  token in the response (`localAuth.login`, `localAuth.register`). Native requests send no `Origin`, which the origin
  policy and Hono's CSRF check let through; the Bearer token is the credential.
- Google sign-in is a browser redirect that ends in the `google_session` cookie. A native app has no such cookie.

## Decision
1. **One Flutter app for Android and iOS.** All screens, state and API calls are Dart and shared. Code that only one
   platform can run lives in Kotlin (Android) or Swift (iOS) inside Flutter plugins in `mobile/packages/`, behind a
   Dart interface generated by Pigeon. The app asks a plugin what the phone can do and shows only what works there.
2. **`mobile/` at the root, a Dart pub workspace.** `mobile/app` is the application; `mobile/packages/smartspend_api`
   (the API client, pure Dart), `mobile/packages/smartspend_ui` (design tokens, theme, components) and
   `mobile/packages/bank_capture` (the native plugin) are its parts. The existing folders do not move into
   `apps/*`: the atlas, the git hooks, Docker, CI and the worktrees open against this repository all name today's
   paths, and the separation that matters (its own build, its own checks, its own release) comes from the folder
   and path-filtered CI, not from a rename. A move can still be its own decision once nothing depends on the old
   paths.
3. **The same API, no mobile-only API.** The app calls the existing tRPC procedures over HTTP: a query is
   `GET /api/trpc/<path>?input=<json>`, a mutation `POST /api/trpc/<path>` with a JSON body, with the session token
   as a Bearer header kept in the Keychain or Keystore. Server work for mobile goes into the procedures and routes
   both clients use.
4. **The procedure list is a generated fact.** `npm run atlas` writes
   `mobile/packages/smartspend_api/lib/src/generated/procedures.g.dart`, one constant per procedure with its path,
   kind and builder, from the same extraction as `docs/atlas/api.md`. The client accepts only those constants, so a
   procedure renamed or removed on the server stops the mobile build instead of failing on a phone, and
   `atlas:check`, the hooks and the merge driver treat the file like the rest of the atlas. Input and output types
   are written by hand in Dart for now, each with a test against a recorded answer; generating them from the zod
   schemas needs the router loaded without its services and is a later step.
5. **Bank and wallet messages, per platform.**
   - Android: the notification listener moves into the Flutter app's Android code (`bank_capture`), installed from
     the Play Store. It keeps its own queue and uploads from Kotlin, so capture works while Flutter is not running,
     and it posts to the existing `POST /api/sms/ingest` with the user's webhook token, which the app fetches after
     sign-in. The companion app is retired once this ships.
   - Android SMS permissions (`READ_SMS`, `RECEIVE_SMS`) are not requested. Google Play lists "SMS-based money
     management" as a possible exception, but grants it only after a declaration and review, and only when no
     other method gives the core feature; the notification listener does. Reading the SMS inbox (for example to
     import past months) would be its own decision with its own Play declaration.
   - iOS gives no app access to SMS or to other apps' notifications. The app exposes an App Intent ("record a bank
     message") that a Shortcuts automation on incoming messages runs, without confirmation since iOS 17, and that
     posts with the app's own session, so no token sits in a public Shortcut. A share extension records any shared
     text, and a WidgetKit widget shows the month's budget.
   - Live Activities are for things that end: they stay active for at most eight hours and on the Lock Screen for at
     most twelve. A running budget belongs in the widget; an ongoing voice call is a fit.
6. **Offline first, the same rules as the web app.** Each account gets its own local SQLite store (drift); screens
   read it, and writes go through an outbox sent in order once the network is back. The ledger stays the server's:
   days and months are Cairo business time computed on the server (golden rule 6).
7. **The web app stays.** The browser and PWA build keeps serving everyone without the store app. The Capacitor
   shells and the companion app stay until the Flutter app reaches parity on their platform; the store listing then
   moves to the Flutter build under the same id, `com.smartspend.app`. Debug builds use `com.smartspend.app.dev`,
   so they install next to a store build.
8. **Stack.** Riverpod for state, go_router for navigation (a shell route for the bottom bar), Flutter's gen-l10n
   with Arabic as the source language and English optional (decision 0020), `flutter_secure_storage` for the session
   token, `local_auth` for the app lock, `package:http` in the API client. Versions are pinned in `pubspec.lock`;
   the Flutter version CI uses is pinned in `mobile/pubspec.yaml`.
9. **CI checks every change under `mobile/`**: formatting, analysis and tests of every package, an Android debug
   build (Kotlin compiles) and an iOS build without signing (Swift compiles). Store releases (Fastlane, signing,
   store listings) are added when the store accounts and keys exist; until then there is no release configuration
   that cannot run.

## Consequences
- A procedure change on the server shows up in the generated Dart file in the same commit, and the mobile workflow
  fails if Dart code still calls the old one. Changing an input or answer shape is still caught only by the Dart
  tests written for it.
- Google sign-in on mobile needed a server change first: `auth.signInWithGoogle` accepts a Google ID token from the
  native sign-in SDK, checks it (`api/lib/google-id-token.ts`), and returns a session token like a phone login.
- The Android app will ask for notification access from a store install, which Play reviews against its policy
  and which the Data safety form must disclose.
- iOS capture needs the user to set up one Shortcuts automation once; it is not automatic like Android.
- Two clients now consume the API. A breaking change to a procedure must keep the version that store builds still
  in users' hands call, until those builds are retired.
- iOS builds need macOS: CI uses GitHub's macOS runners, and releases will too.

## Milestones
1. Foundation (this record): workspace, client, catalog, tokens, shell, bridge, CI.
2. Sign-in (built): `auth.signInWithGoogle` on the server, which accepts only ID tokens Google signed for the app's
   own Android and iOS clients (`GOOGLE_ANDROID_CLIENT_IDS`, `GOOGLE_IOS_CLIENT_IDS`); in the app, phone login, sign-up
   with WhatsApp verification (Turnstile in a web view, the code sent through a `wa.me` link, `/api/sse/otp` followed
   across app switches) and Google through `google_sign_in`; the token in `SessionStore`, the user from `auth.me` or
   `localAuth.me`, a route guard on every tab, and a token the server refuses forgotten at once. Google stays hidden
   until its client ids are configured ([accounts](../systems/accounts.md), known issues 8 to 11).
3. The ledger (first part built): the record tab with the month's totals from `expense.getMonthSummary` and the
   latest transactions by day; recording by text through `ai.parseExpense`, saved at once, after a review sheet or
   after the server's question (`expense.answerClarification`), each save with a request id and an undo; the full
   list a page at a time, with swipe-to-delete that waits for its undo to expire. Offline (built): every sentence
   goes through an outbox kept on the phone, shown at once, and read and saved in order when the network returns,
   with the web's offline rules (the sentence check and the plan's `offline.limit` from `ai.getUserLimits`); the last
   month totals and transactions seen stay on screen offline. The outbox and that copy are one JSON file per
   account in the app's private folder, as the web keeps its queue in one JSON list; SQLite (point 6) comes when
   the app keeps the whole ledger offline. The app lock (built): its own plugin, `device_lock`, instead of
   `local_auth` (point 8), as [decision 0023](0023-mobile-app-lock.md) explains. The English interface (point 8,
   decision 0020) is a phone preference, switched in More or on the sign-in screen.
4. Android capture: the listener, queue and upload in `bank_capture`, the setup flow; retire `android-app/`.
5. iOS capture and extras: the App Intent and automation guide, the share extension, the widget; voice calls on
   both platforms over `/api/voice/v2`.
6. Release: signing, store listings, privacy labels and Data safety, Fastlane, staged rollout; retire the Capacitor
   shells.
